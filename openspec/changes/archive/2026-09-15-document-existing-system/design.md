## Context

当前系统由 Taro 4 + React 18 前端和 NestJS 10 后端组成，前端通过 `Network` 访问相对路径 `/api/...`，后端使用 Supabase/PostgreSQL 集合和 Coze SDK 中的 S3Storage。此次工作是对已有代码进行反向建档，规格来源限定为当前页面、控制器、服务和构建配置中已经存在的行为。

## Goals / Non-Goals

**Goals:**

- 以用户或 API 调用方可观察的行为描述现有系统，而不是复述类名、文件结构或框架选择。
- 按业务能力拆分主规格，让后续菜谱、AI、周计划、字典和平台改动可以定位到独立契约。
- 明确当前系统的降级和兼容行为，包括 AI 模板降级、旧版周计划对象结构和 TOS 签名失败回退。
- 在不修改运行时代码的前提下完成规格同步和变更归档。

**Non-Goals:**

- 不补齐登录鉴权、真正的用户体系、图片上传接口或个人统计接口；这些目前没有完整实现。
- 不修复代码中的分类不一致、乐观点赞回滚缺失或前端静态统计等问题，只将可观察现状记录为后续变更的基线。
- 不把 ESLint、Tailwind、pnpm、Taro 等开发规范写入产品行为规格；这些继续由 `AGENTS.md` 和项目配置约束。
- 不迁移或修改数据库结构。

## Decisions

### Decision 1: 按业务能力而不是前后端文件拆分规格

菜谱生成、周计划保存和首页展示是跨页面、控制器和数据表的连续流程。按业务能力建档可以在同一份规格中覆盖完整用户结果，同时把网络、存储和环境约定放入独立平台契约。

备选方案是为前端页面和后端模块分别建规格，但那会让“生成后入库再从首页打开详情”这种跨端流程分散在多份文档中，也容易把实现边界误当成产品边界。

### Decision 2: 只记录当前已经存在的行为

规格明确记录默认用户标识、未实现按钮提示、静态个人统计和无图片时的占位展示。这样做的目的不是认可这些实现，而是让未来变更可以准确判断“新增行为”和“既有行为”。

备选方案是按目标产品补写理想规格，但那会形成无法由当前代码满足的契约，不适合本次“已有代码归档”任务。

### Decision 3: 将基础设施可依赖行为集中为平台契约

`/api` 前缀、`{ code, msg, data }` 信封、POST HTTP 200、相对路径域名拼接、Supabase 环境凭据和 TOS 预签名 URL 会影响所有业务模块，因此集中记录在 `service-platform-contracts`，业务规格只引用其输入输出，不重复实现细节。

### Decision 4: AI 输出同时记录结构化结果和失败降级

AI 菜谱和周计划都依赖外部模型响应，当前服务会解析模型返回中的 JSON；当调用失败或返回无法解析时，使用内置模板返回可用结果。规格将降级作为系统行为，而不是隐藏为实现细节。

## Risks / Trade-offs

- 部分集合结构没有完整出现在 Drizzle schema 中，例如 `recipe_saves`、`dictionaries` 和运行时使用的 `image_key` 字段；规格依据服务实际读写行为记录，后续数据库整改应另行建变更。
- 前端个人中心的统计数字和部分菜单项是静态或提示性交互，规格只能承诺页面展示与导航反馈，不能承诺真实账户数据。
- AI 输出字段由模型生成，当前代码只做有限归一化；规格要求关键字段存在，但不对模型创意结果的具体菜名作固定断言。
- 本次只执行 OpenSpec 校验和现有 TypeScript/构建配置核对，不调用需要真实 Supabase、TOS 或模型凭据的线上接口。
